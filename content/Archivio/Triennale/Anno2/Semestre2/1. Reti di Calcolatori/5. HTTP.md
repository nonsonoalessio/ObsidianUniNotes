# HTTP: il protocollo del Web
| Protocollo di Trasporto | Porta dedicata |
|---|---|
| TCP | 80 |

## Pagina web

Il protocollo HTTP richiede che vi sia il trasferimento di un documento, chiamato *web page* tra un client ed un server. Ciascuna web page è composta da più elementi, detti *objects*, che possono essere file HTML, immagini e altri tipo di risorse; questi sono inclusi in un *base HTML-file* che viene recuperato, alla richiesta, dal client, che include i vari oggetti (i *referenced objects*).
Esistono 3 tipi di pagina web:
- pagina **statica**: il contenuto è già fissato e non varia;
- pagina **dinamica**: il contenuto è generato al momento dell'accesso (può dunque variare);
- pagina **attiva**: esegue un programma sul computer del client^[Queste sono poco utilizzate, in quanto sono facili vettori di minacce informatiche.].

### URL
%%(RFC 3986)%%
Ciascun oggetto è rappresentato da una stringa, detta URL (Uniform Resource Locator), che identifica in maniera univoca l'indirizzo di quella risorsa.

Un'URL ha una forma del tipo:
>[!tip] URL: forma tipica
>```protocollo://[username[:password]]@host[:porta]</percorso>[?querystring][#fragment]```

- **protocollo**: specifica il protocollo da utilizzare per richiedere una data risorsa;
- **username:password** *opzionali*, sono le credenziali di accesso alla risorsa^[Non è un metodo sicuro per trasmettere le credenziali, in quanto viaggerebbero in chiaro.];
- **host[:porta]**: è l'identificativo su cui risiede la risorsa, mentre il campo `porta` è *opzionale*;
- **percorso**: è il path all'interno del filesystem del server ove è locata la risorsa; quando non configurato, si può impostare il server per fornire una pagina di default;
- **querystring**: *opzionale*, si può utilizzare per passare al server dei parametri, nella forma `?parametro1=value1&parametro2=value2`;
- **fragment**: indica una posizione determinata all'interno della risorsa.

# Funzionamento di HTTP

1. Il client inizializza (crea una socket) una connessione TCP con il server^[È la fase di handshake.], sulla porta `80`;
2. Il server accetta la connessione^[Fine della fase di handshake.];
3. Avviene lo scambio di messaggi HTTP tra client e server sulla connessione TCP appena aperta;
4. La connessione è chiusa.

## Connessione persistente e non persistente

Agli albori (versione 1.0) di HTTP, si utilizzava una connessione TCP *non persistente*: veniva richiesto di aprire una connessione TCP per ogni oggetto da richiedere, ciascuna delle quali era poi chiusa alla recezione, da parte del client, dell'oggetto.

Questo approccio non è molto efficiente, specie odiernamente: se una pagina avesse molti oggetti da dover recuperare per essere composta, si aprirebbe un numero spropositato di connessioni TCP parallele con il server, causando problemi di congestione a questo che si troverebbe in chiara difficoltà nel servire in breve tempo tutti i client.

Con le nuove versioni del protocollo, si è scelti di implementare delle connessioni TCP *persistenti*: queste restano dopo la recezione del singolo oggetto e possono essere sfruttate per richiedere più oggetti della pagina, alleggerendo l'aggravio sul server, e migliorando la responsività generale riducendo la latenza[^bignote].

[^bignote]: 
    Caricare una web page sfruttando delle connessioni TCP non persistente, richiede 2 RTT per oggetto (fase di handshake), più il tempo di trasmissione dello stesso file:
    $$loadTime= 2 \ RTT + d_{trasmission \ time}$$
    Con una connessione persistente, dopo la fase di handshake che avviene prima della richiesta del primo oggetto, questa resta aperta: la latenza viene abbattuta ad un solo RTT per oggetto (quello della richiesta), essendo le altre risorse recuperate mediante la stessa connessione.

## I metodi di HTTP
| Introdotti (HTTP Version) | Metodi |
|---|---|
| HTTP 1.0 | `GET`, `HEAD`^[La differenza tra `GET` e `HEAD` risiede nel fatto che, sebbene siano entrambi utilizzati per richiedere una risorsa, `GET` richiede informazioni sul contenuto e la risorsa stessa, `HEAD` ne richiede, invece, solo le informazioni.], `POST` |
| HTTP 1.1 | As before + `PUT`, `DELETE` ^[L'utilizzo di questi metodi è spesso bloccato in quanto potenzialmente dannoso per la pagina web ed il web server. Sono utilizzati principalmente dai web masters per caricare e rimuovere oggetti da un web server.] |
Questi metodi, utilizzati nelle richieste, vengono inoltrati al server, che produce un messaggio di risposta. Entrambi i messaggi sono in formato testuale, con codifica ASCII e *human readable*, con carattere di fine linea CRLF^[Ciò significa che è presente sia la sequenza di escape (control character o *bytecode*) del ritorno ad inizio linea (`r`, *carriage return*), che la sequenza per andare ad una nuova riga (`n`, *line feed*).].

### Messaggio di richiesta

``` HTTP
GET /index.html HTTP/1.1\r\n 
Host: www-net.cs.umass.edu\r\n 
User-Agent: Firefox/3.6.10\r\n 
Accept: text/html,application/xhtml+xml\r\n 
Accept-Language: en-us,en;q=0.5\r\n 
Accept-Encoding: gzip,deflate\r\n 
Accept-Charset: ISO-8859-1,utf-8;q=0.7\r\n 
Keep-Alive: 115\r\n 
Connection: keep-alive\r\n 
\r\n
```

| Attributo | Significato |
|---|---|
| `Cache version` | Informazioni sulla cache. |
| `MIME-Version` | Specifica la versione MIME^[**Multipurpose Internet Mail Extension**. Specifica come interpretare i byte del body, in modo da ricostruire il file trasmesso in maniera testuale.] |
| `If-Modified-Since` | Se modificato da una certa data. |
|`Accept-Encoding` | Codifiche supportate. |
| `Accept-Language` | Linguaggi in cui si preferisce visualizzare una pagina (se presenti, altrimenti default a una lingua scelta dal programmatore). |

Una richiesta viene spesso effettuata mediante l'utilizzo del metodo `GET`, mentre si utilizza il metodo `POST` (includendo nel body le informazioni da trasmettere) per inviare qualcosa al server (eg.: un form). 

Anche `GET` è utilizzato per inviare delle informazioni al server, ma questo metodo presenta alcuni svantaggi dati dal dover inserire le informazioni da trasmettere all'interno dell'URL, tra cui:
- le informazioni viaggerebbero in chiaro;
- non vi è la stessa chiarezza e leggibilità offerta da inserire gli stessi dati nel body^[Questo, tuttavia, costringe il server a vedere il body della richiesta (e non solamente l'URL, come avverrebbe in una `GET`), causando una minore efficienza in termini di computazione.].

### Messaggio di risposta

```HTTP
HTTP/1.1 200 OK\r\n 
Date: Sun, 26 Sep 2010 20:09:20 GMT\r\n 
Server: Apache/2.0.52 (CentOS)\r\n 
Last-Modified: Tue, 30 Oct 2007 17:00:02 GMT\r\n 
ETag: "17dc6-a5c-bf716880"\r\n 
Accept-Ranges: bytes\r\n 
Content-Length: 2652\r\n 
Keep-Alive: timeout=10, max=100\r\n 
Connection: Keep-Alive\r\n 
Content-Type: text/html; charset=ISO-8859- 1\r\n 
\r\n 
data data data data data ...
```
| Attributo | Significato |
|---|---|
| `Accept-Range` | Valori accettabili. |
| `Data` | Data di creazione della risorsa. |
|  `Content-Language` | Lingua del contenuto. |
|  `Content-Encoding` | Codifica del contenuto. |
|  `Last-Modified` | Data di ultima modifica. |

Ad ogni risposta è associato un codice di stato: 

| Codice | Stato |
|---|---|
| `100`, Informational | Richiesta ricevuta, continua l'elaborazione^[Non molto usato, si preferisce lo stato `200` per maggiore informazione.]. |
| `200`, Success | L'azione è stata ricevuta, compresa ed accettata. |
| `300`, Redirection | Il client deve compiere ulteriori azioni per soddisfare la richiesta. |
| `400`, Client Error | La richiesta non è sintatticamente corretta o non può essere soddisfatta. |
| `500`, Server Error | Il server non può soddisfare una richiesta apparentemente valida.

# Versioni di HTTP
## HTTP 1.1
Viene introdotta la possibilità di fare molteplici richieste `GET` su singola connessione TCP. La logica per servirla è FCFS (First Come, First Served). Questo causa agli oggetti piccoli di dover aspettare la trasmissione degli oggetti grandi inseriti prima di loro: il fenomeno è detto Head-Of-Line blocking (HOL Blocking).

## HTTP 2
HTTP 2 si pone come un miglioramento delle novità introdotte da HTTP 1.1, pur mantenendo la retrocompatibilità con questo^[I metodi sono i medesimi: se uno dei due host non supporta HTTP 2, la richiesta verrà ugualmente processata come una in versione 1.1.]. 

In particolare, si cerca di mitigare il problema dell'HOL Blocking, sia assegnando una priorità specifica a ciascun elemento^[Viene meno la logica FCFS, scaricando prima gli elementi a priorità elevata.], sia realizzando il *framing* dei messaggi.

Il framing^[Per realizzare il framing, vi è bisogno che, a livello applicativo, via sia un sottolivello dedicato esclusivamente al framing. I pacchetti, inoltre, dovranno recare delle intestazioni con delle informazioni di controllo utili per ricostruire il messaggio originale nel corretto ordine.] dei messaggi HTTP 2 avviene dividendo in blocchi una pagina web da trasmettere: ogni blocco conterrà una porzione di ciascun oggetto di cui la pagina si compone; ad ogni istante di tempo, dunque, si scarica una parte di ciascuna risorsa che compone una pagina web, creando nell'utente la percezione che la pagina web sia - almeno parzialmente - già navigabile, anche senza aver scaricato subito tutti gli oggetti.

## HTTP 3
Nel tentativo di migliorare ulteriormente HTTP, si è in fase di adozione di HTTP 3. Questo standard prevede un'implementazione su UDP per evitare che la perdita di oggetti su connessione TCP causi ritardi (di ritrasmissione) ed implementa, a livello applicativo, delle estensioni native per la sicurezza della comunicazione, il controllo della congestione e degli errori.

# Stateful HTTP: cookies

HTTP nasce come protocollo *stateless*: ciascuna richiesta è soddisfatta senza tener conto delle precedenti.

Tuttavia, per offrire un'esperienza personalizzata agli utenti, si implementano i *cookies*.

Il meccanismo di funzionamento dei cookies prevede che, alla prima visita di un sito web, il server che risponde creerà un'entry nel suo database nel backend, associata ad un ID attribuito all'utente. Alla visita successiva, l'utente includerà, nell'header della richiesta HTTP, una linea con l'ID del cookie.

# Caching web: proxy server

Per migliorare l'efficienza della navigazione web, si fa spesso ricorso a dei server intermedi, detti *proxy servers*. Lo scopo è quello di avvicinare i contenuti all'utente e ridurre il carico di lavoro sui web servers, creando una copia della pagina sui proxy server mediante una richiesta all'origin server alla prima richiesta di un host, per poi servire qualsiasi altro client che fa richiesta per la stessa risposta mediante il proxy, senza ritornare per l'origin server.

Questo meccanismo viene implementato mediante il `CONDITIONAL-GET`, una richiesta di tipo `GET` che include l'attributo `IF-MODIFIED-SINCE`. Assumendo che il proxy server abbia già una copia della risorsa con cui rispondere (altrimenti dovrebbe richiederla all'origin server mediante una tradizionale `GET`), questo contatterà l'origin server richiedendo il contenuto, includendo nella richiesta l'attributo `IF-MODIFIED-SINCE`; questo potrà rispondere in due modi:
- `STATUS 304`: la pagina non è stata modificata entro l'intervallo di tempo che occorre tra la data di `IF-MODIFIED-SINCE` e l'istante attuale, quindi il proxy server inoltra la risorsa al client che ne ha fatto richiesta senza ulteriore intervento dell'origin server;
- l'origin server risponde con la risorsa: questo avviene perché la risorsa è stata modificata; l'origin server, dunque, non terrà più conto del campo `IF-MODIFIED-SINCE` e la `CONDITIONAL-GET`diventerà *de facto* una classica `GET`. Il proxy server provvederà a salvare in cache questa risposta.
