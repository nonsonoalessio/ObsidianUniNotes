# DNS: la risoluzione dei nomi
| Protocollo di Trasporto | Porta dedicata |
|---|---|
| UDP | 53 |
| TCP^[In caso di problemi, DNS viene implementato su trasporto TCP. Questo avviene quando un'eventuale risposta risulta essere troppo grande per essere spedita in un solo pacchetto UDP (l'attributo `TRUNCATED` nella risposta indicherà proprio l'incompletezza del messaggio) e viene divisa in più pacchetti, trasmessi via TCP così da poter essere ricostruiti nel corretto ordine.] | 53|
## A cosa serve DNS?
Vi sono diversi modi per identificare gli host sulla rete. Tra questi, per comodità di fruizione dei contenuti, vi è l'hostname, quale può essere un URL. Tuttavia, un calcolatore non potrebbe lavorare bene con questo modello poiché:
* un URL non fornisce alcun informazione utile su dove un server possa trovarsi all'interno della rete;
* avendo dimensione variabile, un calcolatore non lavorerebbe bene in termini prestazionali esclusivamente sulla URL.

Quello che si preferisce fare è, invece, attribuire ad ogni hostname un indirizzo numerico (l'indirizzo IP); si pone dunque la necessità di "tradurre" ciascun hostname in un indirizzo IP, mantenendo l'*ease of use* dei nomi contemporaneamente alla buona prestazionalità dei calcolatori.

A tal proposito sono dedicati dei DNS^[**Domain Name System**.] server, delle macchine solitamente UNIX su cui è in esecuzione BIND.

## Servizi offerti da DNS
Oltre alla traduzione dei nomi, DNS offre i seguenti ulteriori servizi.

### Host Aliasing
Un nome complicato può avere diversi sinonimi. Ad esempio, `relay1.us-west.domain.com` può avere due alias (più facili da ricordare) come `www.domain.com` e `domain.com`. Sarà cura del DNS individuare la corrispondenza tra `domain.com` (alias) e `relay1.us-west.domain.com` (canonical name).

### Mail server aliasing
Analogamente e per le stesse cause, potrebbe verificarsi la stessa situazione anche nel caso dei mailservers. Il DNS svolgerà una funzione analoga anche in questo caso, risolvendo un alias col canonical name.

### Load balancing
Nel caso di copie della stessa risorsa (ad es. una pagina web) replicata su più macchine, il DNS può aiutare a distribuire il carico per evitare congestioni su uno o più nodi.

In questo caso, si prevede di assegnare lo stesso hostname a più macchine con indirizzi IP differenti. Quando verrà chiesto al DNS di risolvere quell'hostname, il DNS risponderà sempre con tutti gli indirizzi IP associati a quell'hostname, rotandone l'ordine. L'effetto "load balancing" si ottiene poiché, di solito, il client che effettua la query andrà a contattare di default il primo indirizzo IP contenuto nella risposta. 

Questo meccanismo è adoperato anche per far sì che più mailservers condividano lo stesso nome.

# Architettura di DNS
## Principio di funzionamento
1. Quando un'applicazione ha bisogno di risolvere un nome invoca il lato client di DNS, specificando il nome da risolvere^[Sui sistemi UNIX, solitamente questo si ottiene chiamando la funzione `getbyhostname()`.];
2. Il DNS prende il controllo ed effettua una *query* sulla rete, utilizzando UDP come trasporto, sulla porta `53`;
3. Il client DNS riceve la risposta e la passa all'applicazione che ne ha fatto richiesta.

## Implementazione
### Impossibile l'implementazione centralizzata

Non è pensabile implementare DNS seguendo uno schema centralizzato per i seguenti motivi:
- **single point of failure**: se andasse giù il singolo server DNS su cui tutta l'Internet fa affidamento, Internet stessa non funzionerebbe correttamente;
- **volume di traffico**: un solo server si troverebbe a gestire tutte le richieste di traduzioni presenti sull'Internet; non sarebbe possibile a causa della congestione che si creerebbe;
- **database distante**: ovunque lo si posizioni fisicamente, il singolo server DNS risulterebbe sempre distante dalla maggioranza degli utenti, con un conseguente calo prestazionale;
- **manutenzione**: un singolo server dovrebbe contenere *tutte* le corrispondenze dell'Internet, necessitando di frequenti manutenzioni (per inserire nuovi record).

### Approccio distribuito (e gerarchico)
Il servizio DNS viene implementato con un gran numero di server sparsi per il mondo, organizzati in maniera gerarchica. La peculiarità è che nessun server DNS conosce le corrispondenze per ciascun nome, ma saprebbe come ricavarle.

Ricordando la struttura tipo di un URL:
>[!tip] Struttura di un URL
> ```subdomain.domain.TLD.```
> Ad esempio: `aws.amazon.com.`

si stabilisce che la gerarchia dei server DNS prevede 3 classi di server DNS:
- **root server**: è deputato a risolvere la parte `.` che, in soldoni, equivale a ==fornire l'indirizzo del DNS server per il TLD==. Esistono 13 root servers (di cui esistono ca. 1000 copie), gestiti da 12 organizzazioni differenti e coordinati dalla IANA;
- **top-level domain server**: risolve la parte `.TLD` che, in soldoni, equivale a fornire l'indirizzo del *server autoritativo* per il dominio;
- **Authoritative DNS server**: è il server che sa con certezza qual è l'indirizzo dell'host desiderato.

Prima di arrivare all'authoritative DNS server può essere necessario passare per server intermedi, che rimanderanno ad ulteriori name servers autoritativi per un dato sottodominio^[Può essere l'esempio dei sottodomini dell'Uni.].

#### DNS Caching
Per la massima efficienza, analogamente ad HTTP, si pensa di inserire, nella gerarchia, dei proxy server, detti *local name server*, che sono generalmente posti sulla rete dell'ISP e quindi vicini agli utenti^[Talvolta, l'ISP può forzare ad utilizzare i propri DNS server piuttosto che quelli di terzi, intercettando tutte le richieste sulla porta `53` UDP/TCP, e rispondendo in modo trasparente rispetto all'utente. Questo fenomeno viene detto **Transparent DNS proxying**.] ^[Può anche capitare che il sistema operativo scelga di utilizzare i server DNS di default piuttosto che quelli specificati dall'utente. In questo caso, si parla di **DNS leak** e può rappresentare un serio problema per la privacy, in quanto le queries possono essere loggate ed utilizzate per fini di monitoraggio, ad esempio.].

Sono proprio i local name servers ad effettuare, normalmente, le richieste alla gerarchia dei server sopra descritta[^bignote], per poi salvarla in cache così da poterla presentare più velocemente qualora si verifichi il caso di una nuova richiesta in un breve periodo di tempo. 

Dal momento in cui le associazioni nome-indirizzo possono non essere permanenti, il valore della risposta presenta un "conto alla rovescia" entro il quale la validità dell'associazione non avrà più valore: questo intervallo è definito come TTL (Time To Live).

[^bignote]: Si parlerà di:
    - richiesta *iterativa*, se viene immediatamente soddisfatta; è il caso di un server DNS di livello più alto nella gerarchia che restituisce, ad esempio, l'indirizzo di un DNS server autoritativo, cui verrà posta la richiesta;
    - richiesta *ricorsiva*, se ha bisogno di passare per più macchine per ottenere una risposta; è il caso del local name server che interpella, per conto del richiedente, prima il root server e poi i restanti server a livelli inferiori della gerarchia.
    Si distingue anche tra:
    - risposta *autoritativa*: se a fornirla è proprio il DNS server autoritativo per quel dominio/sottodominio;
    - risposta *non autoritativa*: se è ancora nell'intervallo di validità del TTL e proviene dalla cache di un DNS server non autoritativo.

#### Inserimento di un record nel database
Per inserire un nuovo record all'interno del database DNS bisogna rivolgersi ad un ente di registrazione, detto *registrar*, che ha, previa verifica dell'unicità del nome, proprio questo compito; esistono svariati registrar, sotto il coordinamento della ICANN.

Quando si registra un nome di dominio, è necessario fornire gli indirizzi dei DNS server primario e secondario autoritativi^[Per evitare disruptions dovute al SPoF, è richiesto che i due (o più) server risiedano su reti diverse.] per quel dominio, in cui inserire il record `A` (ed eventualmente `MX`) dei propri services servers (web servers, mail servers etc).

# Transazioni DNS

## Record DNS
I DNS server che implementano il database distribuito DNS memorizzano i *Resource Records*; questi sono inclusi in una riposta DNS.

Un record DNS contiene 4 campi:
>[!tip] RR: campi
>```(Name, Value, Type, TTL)```

 Il campo `TTL` rappresenta la quantità residuale di tempo di validità di un certo record, oltre la quale il record viene eliminato dalla cache del DNS server, mentre gli altri campi assumono significati diversi al variare di `type`.

##### Type ```A``` record
Un record `A` esprime l'indirizzo IPv4 dell'host, che sarà contenuto nel campo `value`, mentre `name` sarà il nome dell'host per cui si è fatto richiesta.

Il tipo `AAAA` indicherà, analogamente, l'indirizzo IPv6.

##### Type ```NS``` record
Un record di tipo `NS` esprime, nel campo `value`, l'hostname del DNS server autoritativo che consente di ottenere gli indirizzi IP per gli host associati al (sotto)dominio di cui quel server è autoritativo, che sarà espresso nel campo `name`.

`NS` sta infatti per `Name Space`.

##### Type ```CNAME``` record
Un record di tipo `CNAME` esprime, nel campo `value`, il nome canonico dell'host per cui si fa richiesta, contenuto del campo `name`.

`CNAME` sta infatti per `Canonical Name`.

##### Type ```MX``` record
Un record di tipo `MX` esprime il nome canonico, nel campo `value`, del mailserver che ha per alias il valore espresso nel campo `name`.

Mediante questo record è possibile associare, contemporaneamente, lo stesso dominio sia al webserver che al mailserver.

`MX` sta infatti per `Mail eXchange`.

## Messaggio DNS
Un messaggio DNS prevede un'intestazione da 12 B di dimensione con i seguenti campi:
- **ID richiesta** (16 bit), uguale sia nella query che nella response;
- **flags**:
    - 1 bit per indicare se query (`0`) o reply (`1`);
    - 1 bit per authoritative o non authoritative;
    - 1 bit per *recursion-desired* flag (richiesta di ricorsione);
    - (nella risposta) 1 bit per *recursion-available* flag;
- (nella risposta) **numero di occorrenze**.

Il body contiene:
- **sezione delle domande**: contiene informazioni sulle richieste che stanno per essere effettuate, comprensive di nome che sta per essere richiesto e record type della richiesta;
- (nella risposta) **sezione delle risposte**, con la tupla del RR `(Name Value Type TTL)`;
- (nella risposta) **sezione autoritativa**, con i record dei server autoritativi;
- (nella risposta) **sezione aggiuntiva**, con altre informazioni (quali, nel caso di una richiesta `MX`, può essere un record `A` per il server di posta).
